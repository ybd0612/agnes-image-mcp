# RPM 限流设计

> 📚 **本文档隶属 [文档总纲](README.md)** — 关键事实以总纲 §2 SSOT 为准；修改本文档须遵守总纲 §3 同步铁律。

## 1. 适用范围

当前目标账户为 Agnes 免费版 `default`。图片模型 RPM 按请求中的 `size` 档位计算，不按任意像素值自行猜测分档。

| size | default RPM | 推荐最小间隔 |
|---|---:|---:|
| `1K` | 20 | 3 秒 |
| `2K` | 10 | 6 秒 |
| `3K` | 1 | 60 秒 |
| `4K` | 1 | 60 秒 |

第一版只接受四个固定 size 枚举，不接受精确尺寸或根据宽高自行推断档位。

## 2. 限流模型

第一版使用单 MCP 进程内共享 limiter：

- 按 `size` 建立独立桶；
- 每个桶记录请求时间；
- 采用滑动窗口或等价的最小间隔策略；
- 请求在进入上游前占用额度；
- 上游失败不退款，避免重复请求造成真实超限；
- 批量默认串行；
- 不同 size 使用不同桶，但仍共享同一个 MCP 进程生命周期。

必须在 README 中声明：多个 MCP 进程、多台机器之间不共享内存限流状态；若未来需要跨实例统一额度，应引入 Redis 等外部协调器，但不属于第一版。

## 3. 429 处理

收到 HTTP 429 时：

1. 优先读取 `Retry-After`；
2. 等待时间取服务端要求与本地档位间隔的较大值；
3. 无 `Retry-After` 时使用有上限的指数退避；
4. 达到最大重试次数后返回 `UPSTREAM_RATE_LIMIT`；
5. 不将 429 视为可以无限重试的信号。

## 4. 批量语义

默认：

```text
continueOnError = false
```

即任意任务失败后停止后续任务，并返回已完成项与失败项。调用方明确传递 `continueOnError=true` 时，才继续处理剩余项目。

`concurrency` 是批量调用参数，不是环境变量；第一版固定为 `1`，不承诺高并发。重试由服务内部策略控制。

## 5. 测试要求

测试应通过可注入时钟验证 3 秒、6 秒和 60 秒间隔，不在自动化测试中真实等待 60 秒。需要覆盖：同档位串行、不同档位独立、批量失败停止、429 Retry-After、失败不退款和服务实例边界。
